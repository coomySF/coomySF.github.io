# Coomy 部落格三個月內容策略（2026-08 ~ 2026-11）

依據：`.agents/product-marketing.md` v1、既有三篇文章全文、content-strategy 方法論。

---

## 0. 策略前提（一段講完）

這個部落格不是流量生意，是信任生意。讀者是正在導入 AI/Agent 的 Tech Lead 與 EM，他們的三個 JTBD 很明確：**把「快但亂」的感覺講清楚**、**拿到可以帶回團隊的框架**、**確認自己不是唯一撞牆的人**。所以內容以 shareable（thought leadership + 失敗現場）為主體，searchable 為輔——中文圈「AI 團隊導入」「vibe coding 團隊協作」「Agent 驗收」這類搜尋量正在長，但幾乎沒有第一手中文內容，先寫的人就是預設答案。每篇文章維持既有配方：**真實事故 → 可帶走的框架 → 誠實標注還沒驗證的部分**。轉換動作不變：讀完 → 追蹤 Threads @coomysky → 自然認識 SpecFormula。

## 1. Content Pillars（4 個）

### Pillar A：多人 × Agent 的失控現場（事故學）
- **對應 JTBD**：「幫我把 AI 讓我們更快但更亂講清楚」
- **推導**：這是讀者搜尋動機最強、情緒最痛的點（四倍爛攤子、共用 DB 被清）。也是與其他中文內容差異最大的地方——別人寫工具教學，這裡寫事故報告。
- **與產品的關係**：SpecFormula 的問題意識入口，但文章只需要把問題解剖清楚，產品提一句就夠。
- **屬性**：Shareable 為主；「vibe coding 團隊」「AI code review」等詞有 searchable 潛力。

### Pillar B：授權與 Loop 設計（領導機制）
- **對應 JTBD**:「給我可以直接帶回團隊討論的框架」
- **推導**：四種 Agent Loop 與不信任循環是目前最有框架潛力的資產。這個 pillar 負責把框架從「一篇文章」養成「一套可引用的語言」——讀者在 retro、1on1 引用你的詞彙，就是品牌護城河。
- **屬性**：Shareable（框架型 thought leadership），長尾可搜「授權」「ownership」「心理安全」。

### Pillar C：驗收、共識與可複製的生產
- **對應 JTBD**：JTBD 1 + 2 的交集——「每個 task 都完成了，產品卻失控」的解方層。
- **推導**：customer language 裡的關鍵詞全在這裡：驗收、共識、可複製、判斷力。這是離 SpecFormula 最近的 pillar，也最容易寫成行銷腔，所以每篇必須從「沒有工具時你手動可以怎麼做」寫起，工具只當註腳。
- **屬性**：Searchable + Shareable 各半（「BDD 驗收」「spec 過期」「影響分析」有搜尋意圖）。

### Pillar D：主管的身份焦慮與轉型
- **對應 JTBD**：「讓我確認自己不是唯一遇到這些困境的人」
- **推導**：product-marketing.md 明寫 emotional tension 是「我是不是快被 AI 淘汰的主管」。前三個 pillar 治問題，這個 pillar 治人。這類文章分享率最高（讀者轉傳=替自己說話），是 Threads 追蹤成長的主引擎。
- **屬性**：純 Shareable。敢寫自己的懷疑與押錯，就是差異化本身。

## 2. 各 Pillar 題目清單（含 angle 與 JTBD）

### Pillar A：多人 × Agent 的失控現場（6 題）

| # | 題目 | 一句話 angle | 讀者 JTBD |
|---|------|-------------|----------|
| A1 | Agent 把共用 DB 清掉那天，我們才發現沒有人知道「什麼不能動」 | 開發邊界通常不存在於文件裡，只存在於事故之後——把那次事故完整解剖一遍 | 把「快但亂」講清楚；確認別人也炸過 |
| A2 | Code review 變成考古現場：我理解 Agent 改了什麼的時間，比檢查它對不對還長 | AI 沒有降低 review 成本，只是把成本從「檢查品質」搬到「重建脈絡」 | 把 review 越來越累的感覺講清楚 |
| A3 | 兩個 Agent 寫了同一個 Component，我們吵了一下午該留誰的 | 重複實作不是技術問題，是需求切割問題——task 分工切不出 Agent 的修改邊界 | 帶回團隊的分工討論素材 |
| A4 | 「再生成一次」不是在修 bug，是在擲骰子 | 非確定性輸出讓「重跑」失去回歸修復的意義，正確的部分也可能被改壞 | 講清楚為什麼團隊不敢重生成 |
| A5 | 一天三個需求變更：AI 讓變更進得更快，也讓過期的共識活得更久 | 變更速度超過共識更新速度時，最危險的不是沒有 spec，是所有人都拿著舊的 | 把「越快越亂」的機制講清楚 |
| A6 | 一個人帶 Agent 很順，加到第二個人就開始撞——中間到底斷了什麼 | 從 1 到 2 人的臨界點才是 Agent 協作真正的分水嶺，不是人數多寡 | 決定 Agent 導入方式前的參照 |

### Pillar B：授權與 Loop 設計（6 題）

| # | 題目 | 一句話 angle | 讀者 JTBD |
|---|------|-------------|----------|
| B1 | 主管說「這件事交給你」，然後在第三天把它拿回去 | 授權不是死在說出口的時候，是死在第一次偏差出現的時候——解剖那 72 小時 | retro / 1on1 前找語言 |
| B2 | 一次事故讓我把最資深的人切回 Turn-Based，他反而鬆了一口氣 | Loop 不是成熟度階梯：降級不是羞辱，關鍵是切換條件有沒有講明白 | 帶回團隊的 Loop 切換框架 |
| B3 | 我停掉 standup 兩週，才看清楚哪些會議只是我的掌握感 | Time-Based 的檢驗標準只有一個：同步之後，有沒有人因此改變下一步 | 確認不是只有自己在開沒用的會 |
| B4 | 團員每問一次「這個我可以自己決定嗎」，就是我授權失敗一次 | 把這句話當量測指標：它出現的頻率直接反映邊界沒說清楚的程度 | 可直接帶走的自我檢查指標 |
| B5 | 被動團隊的復健：從「等指令」回到「先講判斷」，我們花了多久 | 不信任循環寫了怎麼發生，這篇寫怎麼逆轉——以及哪一步最容易前功盡棄 | 想修復團隊的主管的下一步 |
| B6 | 新人第一個月就給 Goal-Based，失控的不是他，是我的焦慮 | 授權失敗常常不是成員能力問題，是主管無法忍受「看不到過程」的戒斷反應 | 確認授權焦慮是普遍的 |

### Pillar C：驗收、共識與可複製的生產（5 題）

| # | 題目 | 一句話 angle | 讀者 JTBD |
|---|------|-------------|----------|
| C1 | 每個 task 都 done，產品卻不能上線：我們對「完成」有四個版本的定義 | Definition of Done 在 Agent 時代從儀式變成基礎設施——四個人四個版本就是四倍爛攤子的根 | 把整合失控的根因講清楚 |
| C2 | Agent 不會讀你腦中的需求，它只會放大你沒寫下來的那一半 | Garbage in 在 AI 時代不是輸入錯誤，是輸入缺漏——缺的部分 Agent 會自己補，而且補得很有自信 | 講清楚為什麼 prompt 越下越細還是歪 |
| C3 | 驗收條件寫給人看還是寫給 Agent 看？後來發現是同一份 | BDD 情境同時是人的共識文件和 Agent 的停止條件——一份內容，兩種讀者 | 帶回團隊的驗收做法 |
| C4 | 把一次成功變成兩次：團隊的判斷力到底要寫在哪裡才不會蒸發 | 「可複製」的最小單位不是 code，是當時為什麼這樣判斷——以及大多數團隊把它存在最容易蒸發的地方（某個人的腦） | 讓一次成功可複製 |
| C5 | 影響分析不是架構師的專利，是每次變更前十五分鐘的團隊動作 | 「這次改動會碰到什麼」可以是一個十五分鐘的輕量儀式，手動就能做，不需要先買任何工具 | 可立刻試的具體做法 |

### Pillar D：主管的身份焦慮與轉型（5 題）

| # | 題目 | 一句話 angle | 讀者 JTBD |
|---|------|-------------|----------|
| D1 | 我同時開了八個 Agent，然後發現整個團隊的瓶頸是我 | AI 放大的不是團隊產能，是主管這個單點——所有驗收都排隊等同一顆腦 | 確認「更快卻更累」不是自己的錯覺 |
| D2 | 「我是不是快被淘汰的那種主管」——我把這句焦慮拆開來看 | 焦慮拆開後其實是三個可以分別回答的問題：哪些判斷被取代、哪些變貴、哪些還沒人接手 | 讓焦慮變成可處理的清單 |
| D3 | AI 之後，主管的產出不是決定，是團隊下次沒有你也做對的決定 | 把「領導者產出」重新定義成可觀察的東西：你不在場時的正確決策數 | 重新定位自己的價值 |
| D4 | 面試時我押的是「會換方法讓別人往前的人」，AI 時代我才知道押對還是押錯 | 回頭驗證多年前的用人判斷：執行力被 AI 拉平之後，當初那種人到底稀缺在哪 | 用人與育才的判斷參照 |
| D5 | 從 FDE 職缺回推：三年後的 Tech Lead 要會的事，現在的 JD 還沒寫 | 用 OpenAI FDE、AWS ProServe 等公開職缺當證據，反推主管該提前補的能力——不是預言，是讀 JD | 給自己的轉型路線一個外部參照 |

**總計：22 題**（A6 + B6 + C5 + D5）

## 3. 發文節奏建議

現況：一人作業、長文密度高（每篇有文獻與事故細節）、已有「長文 → Threads 變體」的工作流（git log 可見）。

- **長文：每兩週一篇，三個月共 6 篇。** 每週一篇撐不了這種密度，硬撐會先犧牲「敢寫失敗的具體度」，那正是差異化所在。寧可慢，不可稀。
- **Threads：每週 2-3 則。** 每篇長文拆 2-3 個變體（一個事故切片、一個框架單點、一個反直覺句），發佈後分週釋出；長文空窗週用「觀察型短帖」補位（讀者案例回應、框架的新反例）。Threads 是轉換動作本身，不是宣傳渠道。
- **固定發文日**：長文固定週二或週三早上（台灣工程主管的閱讀高峰在通勤與午休），養成讀者的期待節奏。
- **每篇長文文末保留既有的「帶你的案例來對話」邀請**——這同時是下一批題目的 research 來源（讀者案例 = 未來的事故素材）。

### 三個月排程（6 篇長文的優先順序）

| 月份 | 篇目 | 理由 |
|------|------|------|
| 第 1 個月 | **A2**（review 考古）、**B1**（第三天拿回去） | 兩篇都是既有文章的直接續集（見下節），趁三篇創刊文的餘溫把系列感建立起來；A2 痛點最普遍，適合當追蹤成長的引擎 |
| 第 2 個月 | **D1**（八個 Agent、瓶頸是我）、**C1**（四個版本的 done） | D1 串起 Pillar A 與 B 的讀者，把個人焦慮引進來；C1 開始鋪驗收層的地基 |
| 第 3 個月 | **B2**（切回 Turn-Based）、**C3**（驗收寫給人還是 Agent） | B2 讓 Loop 框架長出第二篇（框架要重複出現才會變成語言）；C3 是離 SpecFormula 最近的一篇，放在信任累積三個月後才寫，避免太早像在賣東西 |

未排入的 16 題是第 4 個月起的題庫，依 Threads 迴響動態調整優先序（哪個切片互動高，對應長文先寫）。

## 4. 與既有三篇的關係（自然續集地圖)

```text
《一個人帶 Agent 兩天做完 POC…》(2026-08-05)
├── A1  共用 DB 事件的完整解剖（原文一句「最扯的一次」→ 展開成整篇）
├── A2  review 考古（原文「review 時間花在理解修改範圍」→ 展開）
├── A3  重複 Component 之爭（原文條列的第一種情況 → 展開）
├── A4  再生成一次是擲骰子（原文「不敢把再生成當修正方式」→ 展開）
├── A5  一天三個變更（原文付費路徑實驗段落 → 展開）
├── C1  四個版本的 done（原文「每個 task 都完成不代表能整合」→ 解方層）
├── C2  放大你沒寫下來的那一半（原文 "Garbage in" 一句 → 機制層）
└── D5  FDE 職缺回推（原文末段 FDE/AWS 職缺 → 從佐證變主角）

《不信任團隊的領導者…》(2026-08-05)
├── B1  第三天拿回去（原文行為清單第 3 條「嘴上說交給你」→ 單點深挖）
├── B4  「我可以自己決定嗎」指標（原文「有邊界的自主」五件事 → 量測化）
├── B5  被動團隊的復健（原文寫循環怎麼形成 → 這篇寫怎麼逆轉，最強續集）
├── D1  瓶頸是我（原文「AI 擴大對同一人的依賴」段落 → 展開）
├── D3  沒有你也做對的決定（原文結尾的領導者產出定義 → 展開成方法）
└── D4  面試押注驗證（原文開頭的面試判斷 → 回頭收尾，首尾呼應感最強）

《主管嘴上要 ownership，卻只允許 Turn-Based…》(2026-08-05)
├── B2  切回 Turn-Based（原文「不是成熟度階梯」→ 用真實事故補上原文自承缺少的案例）
├── B3  停掉 standup（原文 Time-Based 段 → 用實驗補證據）
├── B6  Goal-Based 的戒斷反應（原文 Goal-Based 段 → 從主管心理面補）
└── A6  1 到 2 人的臨界點（原文 Loop 視角 × 第一篇的多人現場 → 兩篇的交叉續集）
```

三篇創刊文各自留了「自承還沒驗證」的缺口（Loop 表格需要真實場景、SpecFormula 需要多人驗證、面試判斷沒有追蹤）。**這些缺口就是續集的鉤子：每篇續集都在補上一個前文承諾過的證據，讀者會感覺這個部落格在誠實地還債，而不是在量產內容。**

## 5. 執行守則（防跑偏）

1. 每篇必有一個具體現場（時間、人數、發生什麼），沒有現場的題目退回題庫。
2. 禁用詞照 context：賦能、革命性、顛覆、極致、快人一步。
3. SpecFormula 每篇最多出現一次，且只出現在「如果當時有」的位置；C 系列先寫手動做法。
4. 每篇文末照舊標注「還沒驗證的部分」——這是品牌資產，不是弱點。
5. 三個月後 review：Threads 追蹤數、各 pillar 的互動差異、讀者帶來的案例數（這是最重要的先行指標）。
